# Indexer

Slot deployments, ownership transitions and tax events are indexed by
[Ponder](https://ponder.sh) and served as GraphQL. This is what
[`SlotsClient`](/sdk/client) reads.

## Endpoint

| | |
|---|---|
| Hosted | `https://0xslots-production.up.railway.app/graphql` |
| Local | `http://localhost:42069/graphql` (`pnpm dev:local`) |

Both are exported as `DEFAULT_API_URL` and `LOCAL_API_URL` from `@0xslots/sdk`.

<Callout type="warning">
**One deployment holds every chain.** A subgraph is one deployment per network,
so the chain used to be a property of the endpoint. Here it is a
`where: { chainId }` filter on the query.

An unfiltered list returns base and base-sepolia rows interleaved — a
plausible-looking result that is quietly wrong, which is worse than an error.
`SlotsClient` merges the filter into every list query for you; if you query the
endpoint directly, apply it yourself.
</Callout>

The API is served **unauthenticated**. There is no key to pass, and the SDK
dropped its `apiKey` option accordingly — see [SlotsClient](/sdk/client).

## Shape

Four differences from the subgraph this replaced (`packages/subgraph` is
deleted; these endpoints are the read path):

- Plural fields return `{ items, totalCount, pageInfo }`, not a bare list.
- Pagination is `limit` with `offset`, or the `after` / `before` cursors from
  `pageInfo`. `first` / `skip` are gone.
- Foreign keys are scalar columns; the joined row is the `*Ref` sibling —
  `hook` is an address, `hookRef` is the row.
- There is no `block:` argument. Ponder has no time-travel query.

Every chain-scoped row carries `chainId`.

## Key entities

| Entity | Key fields |
|---|---|
| `slot` | `id`, `chainId`, `recipient`, `currency`, `occupant`, `isOccupied`, `price`, `deposit`, `taxBps`, `collectedTax`, `taxPaidTotal`, `totalCollected`, `hook`, `hookData`, `tenureId`, `createdAt` |
| `hook` | `id`, `chainId`, the `declared*` flags (including `declaredStrict`), `slotCount`, `failedCallCount` |
| `account` | `id`, `type` (EOA/CONTRACT/DELEGATED/SPLIT), `slotCount`, `occupiedCount`, `totalHoldTime` |
| `accountChain` | `account`, `chainId`, `slotCount`, `occupiedCount`, `occupiedAsRecipient` |
| `currency` | `id`, `name`, `symbol`, `decimals` |

A slot points at **one** `hook` (or none). Flags are stored on **both** rows and
they answer different questions: `slot.hook*` is the snapshot taken when the hook
attached — what that slot obeys — while `hook.declared*` is what the hook says
now. They diverge when an upgradeable hook changes its declaration after slots
have committed to it, and comparing them is how you find that.

`slot.hookStrict` is the one worth surfacing: a strict hook's `after` calls run
uncapped and can fail the slot, eviction included.

`hook.failedCallCount` counts `after` calls that reverted and were swallowed. A
hook accumulating those is quietly broken.

`slot` also carries its pending terms, so "what is queued right now" no longer
needs an RPC call per slot: `pendingHasTax` / `pendingTaxBps`,
`pendingHasHook` / `pendingHook` / `pendingHookData`, and `pendingProposedAt`.

`hookData` is the slot's 32-byte configuration FOR its hook — a minimum-tenure
window, say — and it is what lets one hook deployment serve every configuration.
Opaque to the indexer: only the hook knows what the word means.

<Callout type="warning">
Read the `pendingHas*` boolean, not the value column. A `NULL` on a value column
means nothing is queued, but the zero address is itself a real proposed value —
`pendingHook` = zero with `pendingHasHook` = true is a deliberately queued
"detach the hook", not an empty slot.
</Callout>

### `account` vs `accountChain`

`account` has no `chainId` and holds protocol-wide totals. `accountChain` holds
the same counters per chain, and is what a per-chain view must read — otherwise a
recipient list on base shows base-sepolia's recipients with their base-sepolia
counts, and clicking through opens a page that correctly filters by chain and
finds nothing.

`occupiedCount` counts slots the account **occupies**; `slotCount` counts slots
where it is the **recipient**. They describe different roles. The one that pairs
with `slotCount` is `occupiedAsRecipient` — the only honest numerator for an
occupancy percentage.

### A note on schema drift

The indexer serves exactly one schema, and GraphQL rejects a document containing
an unknown field — so an SDK querying a field the deployed indexer does not have
gets an **empty list**, not a clear error. Deploy the indexer and publish the SDK
together.

## Example queries

### List slots

```graphql
{
  slots(
    where: { chainId: 8453 }
    orderBy: "createdAt"
    orderDirection: "desc"
    limit: 10
  ) {
    items {
      id
      recipient
      occupant
      isOccupied
      price
      deposit
      taxBps
      currencyRef { symbol decimals }
      hookRef { slotCount failedCallCount }
      createdAt
    }
    totalCount
    pageInfo { hasNextPage endCursor }
  }
}
```

### Slot activity

```graphql
query GetSlotActivity($slot: String!) {
  boughtEvents(where: { slot: $slot }, orderBy: "timestamp", orderDirection: "desc") {
    items { buyer from price deposit paid timestamp }
  }
  releasedEvents(where: { slot: $slot }, orderBy: "timestamp", orderDirection: "desc") {
    items { occupant refund timestamp }
  }
  liquidatedEvents(where: { slot: $slot }, orderBy: "timestamp", orderDirection: "desc") {
    items { by occupant heldFor timestamp }
  }
}
```

**SDK equivalent:** `await client.getSlotActivity({ slot: "0x..." })`

<Callout type="warning">
**Sales are not indexed yet.** `soldEvent` and `orderCancelledEvent` are gone —
`Slot.sell` was removed, so the events that filled them no longer exist, and
`boughtEvent.viaSell` went with them. A consensual sale now emits `Bought` on the
slot (so occupancy history is complete) and `Filled` on the OfferBook — and the
book is not in `ponder.config.ts`, so the seller's side of a sale is currently
unqueryable. Adding the book to the indexer is what restores it.
</Callout>

### Recipients on one chain

```graphql
query GetAccountChains($chainId: Int!) {
  accountChains(
    where: { chainId: $chainId }
    orderBy: "slotCount"
    orderDirection: "desc"
    limit: 20
  ) {
    items { account slotCount occupiedAsRecipient }
    totalCount
  }
}
```

**SDK equivalent:** `await client.getAccountChains({ limit: 20 })`

## Indexing status

```graphql
{ _meta { status } }
```

`status` is keyed by chain and carries the latest indexed block. There is no
`hasIndexingErrors` counterpart — the indexer stops rather than serving stale
rows behind a flag, so an erroring indexer is a failed request, not a `true`
here.

**SDK equivalent:** `await client.getMeta()`

## Creatives

One hook is indexed: **AdLand**, whose creative is the entire content of an ad
space and lives nowhere else. Everything above is the core protocol, which every
slot shares; a hook is one behaviour among however many people write, and no
other hook is watched.

| Entity | Key fields |
|---|---|
| `creative` | `slot`, `chainId`, `hook`, `uri`, `tenureId`, `publisher`, `clearedAt`, `publishCount`, `firstPublishedAt` |
| `publishedEvent` | `id`, `slot`, `hook`, `uri`, `tenureId`, `publisher`, `timestamp`, `tx` |
| `clearedEvent` | `id`, `slot`, `hook`, `fromTenure`, `toTenure`, `timestamp`, `tx` |

`accountSlot` also carries `publishCount`, counted per account per slot — two
creatives in one tenure count twice.

Two events, and both matter. `Published` is somebody putting an ad up.
`Cleared` is the hook blanking one because the slot changed hands — emitted from
`afterBuy`, `afterRelease` and `afterLiquidate`, with no publish involved.
Reading only the first leaves a creative in the index long after the chain has
stopped serving it.

A clear is **recorded, not applied**: the row keeps its `uri` and gains a
`clearedAt`. That mirrors the contract, which leaves the string in storage and
refuses to return it once `tenureId` has moved on — and it keeps two facts
apart that an empty string cannot hold at once. A slot that has been advertised
on and is now empty is not a slot nobody ever bought.

<Callout>
`creative.uri` is stored whole rather than hashed or resolved. AdLand's
creatives are a few hundred bytes and travel inline as `data:` URIs precisely so
no gateway sits on the render path — so the history needs no gateway either, and
a creative whose IPFS pin has lapsed is still readable here as what was
published.
</Callout>
